\title{\textbf{Pioneer MBR ``Batch F'' Single-File Hang}\\[4pt]
\large Root-cause walkthrough for the Sciex ZT scanning-DIA work}
\author{feat/sciex-zt-scanning}
\date{2026-07-08}

\begin{document}
\maketitle

\section{Symptom}

Every single-file ZT search stalled in the \textbf{Precursor Scoring} stage, at the
match-between-runs (MBR) step, and never reached Chromatogram Integration. The
process stayed alive at only $\sim$2 cores for $>$14 minutes with no new log output
after this line:

\begin{Verbatim}[fontsize=\footnotesize,frame=single]
[..:20:31] [DEBUG1] MBR Batch F: writing per-file MBR sidecars...
\end{Verbatim}

Running the \emph{same} data as a \textbf{3-file} experiment, the identical step
finishes in under a second:

\begin{center}
\begin{tabular}{lll}
\hline
Files & MBR ``per-file sidecar'' step & Whole MBR Batch F \\
\hline
1 file  & $>$14 min (never completes; killed) & --- \\
3 files & $\sim$0.9 s (18:14:49.5 $\to$ 18:14:50.4) & $\sim$3 s \\
\hline
\end{tabular}
\end{center}

So the cost is not proportional to the data size --- one file is dramatically
\emph{slower} than three. That inversion is the tell: the single-file case hits a
degenerate code path, not simply ``more work''.

\subsection{The hot spot (mbr\_streaming.jl:416)}

\begin{lstlisting}[firstnumber=416]
@inline function _nearest_cross_file_donor(donor_dict, pool, target_irt, my_file)
    n = length(pool.irts)
    n == 0 && return nothing
    right = searchsortedfirst(pool.irts, target_irt)   # O(log n): nearest by iRT
    left = right - 1
    @inbounds while left >= 1 || right <= n            # <-- walks OUTWARD across pool
        use_left = ...                                 #     (nearest-iRT-first order)
        pool_idx = use_left ? left : right
        use_left ? (left -= 1) : (right += 1)
        donor = _donor_for_pid(donor_dict, pool.pids[pool_idx], my_file)
        donor !== nothing && return donor              # first CROSS-FILE hit wins
    end
    return nothing                                     # scanned the WHOLE pool, found none
end
\end{lstlisting}

\subsection{The ``different file'' requirement (mbr\_streaming.jl:406)}

\begin{lstlisting}[firstnumber=406]
@inline function _donor_for_pid(donor_dict, pid, my_file)
    entries = get(donor_dict, pid, nothing)
    entries === nothing && return nothing
    @inbounds for e in entries
        e.ms_file_idx != my_file && return e           # <-- must come from ANOTHER file
    end
    return nothing
end
\end{lstlisting}

\section{Root cause}

The counterfactual (``false donor'') feature is, by construction, a donor from a
\emph{different run}: \texttt{\_donor\_for\_pid} only returns an entry whose
\texttt{ms\_file\_idx != my\_file} (line 410--411).

\medskip
\noindent\textbf{With a single file}, no entry can ever satisfy that test. So for
\emph{every} precursor:
\begin{itemize}
\item \texttt{\_nearest\_cross\_file\_donor} does its \texttt{searchsortedfirst}, then
walks \emph{outward over the entire pool} (the \texttt{while} loop, line 427),
calling \texttt{\_donor\_for\_pid} on every member, and \textbf{never finds a
cross-file donor}, so it scans all $n$ pool entries and returns \texttt{nothing}.
\item \texttt{\_resolve\_false\_donor\_for\_pid} then repeats this for \emph{all three}
pools (m/z-bin $\to$ fold $\to$ global), the last of which contains essentially
every precursor.
\end{itemize}

The \texttt{false\_donor\_cache} caches one result per precursor id, so this exhaustive
scan happens once per \emph{distinct} precursor. With $P$ distinct precursors and a
global pool of size $\approx P$:
\[
\text{cost} \;\approx\; P \times P \times (\text{3 pools}) \;=\; O(P^2).
\]
For this data $P \approx 3.5\times10^5$, so $P^2 \approx 1.2\times10^{11}$ dictionary
probes --- i.e.\ the observed 14+ minutes. And the whole effort is wasted: the answer
is always \texttt{nothing}.

\medskip
\noindent\textbf{With $\ge$2 files}, the pool is dense with precursors that
\emph{were} seen in other runs, so the outward walk from the nearest-iRT position
finds a cross-file donor within a handful of steps: $O(\log n)$ per precursor. That is
why 3 files finish the same step in $\sim$0.9~s.

\medskip
\noindent\textbf{In one sentence:} MBR-across-runs is meaningless with a single file
(there is nothing to match \emph{between}), but the code still executes the full
counterfactual search, which degenerates into an always-failing $O(P^2)$ scan.

\section{Proposed fixes}

\begin{enumerate}
\item \textbf{Guard at the dispatch (primary fix).} In
\texttt{score\_precursor\_isotope\_traces} (score\_psms.jl:53), if the experiment has
only one raw file, skip the MBR path and use the existing non-MBR path
(\texttt{\_score\_precursor\_isotope\_traces\_no\_mbr}), emitting a one-line warning.
This is correct: with one file the MBR features would all be ``missing'' anyway. (Care:
files may be split into \texttt{\_fold0}/\texttt{\_fold1} paths, so count \emph{distinct
raw files}, not \texttt{length(file\_paths)}.)

\item \textbf{Belt-and-suspenders (optional).} In \texttt{\_nearest\_cross\_file\_donor}
(mbr\_streaming.jl:416), short-circuit when the pool contains no file other than
\texttt{my\_file} (precompute the set of \texttt{ms\_file\_idx} present once), so any
future no-cross-file-donor situation is $O(1)$ instead of $O(n)$. This leaves all
multi-file behaviour unchanged.
\end{enumerate}

\noindent Fix (1) resolves the reported hang directly; fix (2) hardens the kernel
against the same failure mode in edge cases (e.g.\ a precursor whose entire iRT
neighbourhood is single-file-only).
